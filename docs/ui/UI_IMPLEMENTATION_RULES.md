# PACKSPIRE UI実装基本規則

最終更新: 2026-07-30

## 1. 目的

この規則は、次の二種類の失敗を同時に防ぎます。

1. USSの単純な四角だけでゲーム固有UIを完成扱いにすること。
2. 画像素材を無制限に重ね、画面を装飾コラージュにすること。

目標は「画像の多いUI」ではありません。ホーム画面と同じ作品に見え、
情報が読みやすく、必要な場所だけにゲーム固有の画像部品が使われているUIです。

## 2. 視覚正本の優先順位

画面制作では、次の順に視覚正本を扱います。

1. 実際に動いている現行ホーム画面と共通プロダクトUI
2. 画面用の承認済み参考画像
3. `docs/ui/specs/<screen>.md` の画面仕様
4. Unityで現在読み込まれている実装
5. 外部作品、途中案、生成プロンプト、古いスクリーンショット

外部作品は、情報密度、非対称な構図、操作のリズムなどの抽象的な参考に限定します。
色、枠、アイコン、ロゴ、装飾量はPACKSPIREのホーム画面を優先します。

ユーザーが参考案を承認しても、次の品質検査を省略してはいけません。
承認は、エージェント側の整合性・可読性・実装可能性確認を免除しません。

## 3. 実装開始前の必須ゲート

### 3.1 キャプチャ手段を先に確認する

視覚調整を自動検証する作業では、対象画面をUnityで開き、PNGへ保存できることを確認します。
ユーザーが手動キャプチャで差分を返す運用を指定した場合、エージェント側の自動撮影を必須にしません。
純粋なコード構造整理、コンパイル修正、UXML分離にも撮影ゲートを適用しません。

- Unityが別プロセスでロックされている。
- Game Viewを開けない。
- 対象状態へ遷移できない。
- 指定解像度で保存できない。

自動視覚検証を行う作業で上記のいずれかに該当する場合、全画面の実装を開始しません。
手動確認運用では一画面または一領域ずつ実装し、ユーザーの差分画像を次の修正基準にします。

### 3.2 座標系を確認する

PACKSPIREの現行PanelSettingsは次の設定です。

- Logical reference: 1280x720
- Validation capture: 1920x1080
- Screen match: 0.5

USSの`px`は1280x720の論理座標として設計します。
1920x1080の参考画像座標は、そのままUSSへ書かず、原則として3分の2へ換算します。

画面仕様には必ず次の両方を記録します。

| 種類 | 例 |
|---|---|
| 物理キャプチャ座標 | 1920x1080で x=300, width=600 |
| USS論理座標 | 1280x720で x=200, width=400 |

Game Viewの表示倍率は寸法基準にしません。

### 3.3 ホーム画面からスタイルプロファイルを作る

対象画面ごとの参考案を作る前に、ホーム画面から次を記録します。

- 背景の明るさと情報面の遮光率
- 基本色、強調色、警告色
- 枠線の太さと角の形
- 使用するアイコン系統
- タイトル、見出し、本文、メタ情報の文字階層
- 装飾が置かれる場所と置かれない場所
- 選択状態の表現
- 一画面で同時に見せる情報量

このプロファイルに反する参考案は、ユーザーへ提示する前に修正します。

### 3.4 参考画像の品質ゲート

参考画像を「承認候補」にする前に、ホーム画面と横に並べて確認します。

- 同じゲームの別画面に見えるか。
- 最初に見る主役が一つに定まっているか。
- 装飾枠より内容が目立っているか。
- 背景、パネル、文字のコントラストが安定しているか。
- 主要オブジェクトに四角い画像境界が見えていないか。
- 同じ意味のアイコンや紋章が重複していないか。
- 実際の既存素材または生成可能な素材へ分解できるか。
- 1280x720論理座標へ落としても文字と操作部品が収まるか。

一つでも重大な不合格があれば、承認依頼を出しません。

### 3.5 AI生成モックの扱い

全画面をAI生成した画像は、構図と情報配置のスケッチです。
そのまま制作可能なアート仕様とはみなしません。

AI生成モックを実装候補にする前に、画面内の全主要部品へ次を割り当てます。

| Mock component | Production source | Status |
|---|---|---|
| ヘッダー | 既存のホーム共通素材 | ready |
| 一覧セル | 新規の枠素材を生成 | missing |
| 装備アート | 透明切り抜きを作成 | missing |
| LINKカード | 既存共通部品 | ready |

`missing`が残る状態でコード実装へ進みません。先に部品単位の素材を作ります。

- 全画面画像から文字入り部品を切り出さない。
- 似た既存素材で代用して見た目を変えない。
- 対応素材がない装飾は、削除するか部品として新規作成する。
- 生成モックと既存素材の画風が異なる場合、ホーム画面側へ合わせてモックを直す。
- 「ユーザーが全画面案を承認した」ことを、素材対応確認の代わりにしない。

## 4. 画像素材の役割分類

画像を使う前に、必ず次のどれかへ分類します。

| 種類 | 定義 | 重ねてよいもの |
|---|---|---|
| 完成部品 | 枠、背景、紋章、装飾まで描かれたタブやカード | 文字、必要な状態表示だけ |
| 枠素材 | 内容領域が空で、別の絵や文字を入れる前提 | オブジェクト絵、文字、状態表示 |
| アイコン | 単一の意味を持つ透明画像 | 枠素材または静かな面 |
| オブジェクト絵 | 装備、人物、敵などの主役画像 | 魔法陣、影、専用フレーム |
| 背景 | 画面世界または大面積の環境画像 | 遮光面、情報領域 |

### 4.1 禁止事項

- 完成部品の上へ別の完成部品を重ねない。
- 絵入りタブへ同じ意味の別アイコンを追加しない。
- 装飾済みカードをさらに装飾枠で囲まない。
- 一つの領域で異なる素材世代や画風を無計画に混ぜない。
- 透明余白や元画像の四角い背景を主役アートとして露出しない。
- 低解像度素材を大きく引き伸ばさない。
- 生成画像内の文字や仮アイコンを実装素材として切り出さない。

### 4.2 素材キットの許可表

画面仕様には、領域ごとに使用を許可する素材キットを記録します。

| 領域 | Primary kit | Allowed shared assets | 禁止 |
|---|---|---|---|
| 一覧 | 例: VaultGrid | 共通ロックアイコン | 他世代のタブ、別画風の枠 |
| 詳細 | 例: VaultDetail | 共通LINKカード | 一覧用セルの転用 |

複数キットを混ぜる場合は、色、線幅、角、質感が一致する比較画像を先に作ります。
「既にリポジトリにある」は互換性の根拠になりません。

## 5. 装飾量と視覚階層

「画像優先」は「画像を多用する」という意味ではありません。

### 5.1 装飾予算

- 一つの大領域につき、主となる装飾フレームは一種類まで。
- 画面全体の外枠と全子領域の外枠を同時に強調しない。
- 強い装飾を持つ大領域は、一画面で原則三つ以内にする。
- 繰り返しセルの通常状態は細い枠にし、角飾りや発光を選択セルへ集中する。
- カードの中へ別のカードを置かない。
- 同じ100論理px以内で強い発光線を複数競合させない。
- 四隅装飾は画面または大領域の境界に限定する。
- 通常状態は静かにし、選択状態だけが強く見えるようにする。
- マゼンタ、シアン、金を同じ強度で同時に発光させない。
- 装飾が内容より先に目に入る場合は減らす。
- 画面の25%以上を、強い枠・発光・文字のない静かな領域として残す。

### 5.2 主役を一つにする

画面を見た最初の1秒で、次が判別できる必要があります。

1. どの画面か。
2. 何が選択されているか。
3. 次に操作できる場所はどこか。

一覧、主役アート、効果カード、ヘッダーを同じ強さにしません。
選択中オブジェクトを第一、操作対象を第二、補助情報を第三の階層にします。

### 5.3 背景と情報面

- 背景世界は感じられる程度に残す。
- 文字の背後では、静かな専用面または十分な遮光を使う。
- 情報面を半透明にしすぎて背景の線と文字を競合させない。
- 画面全体を一枚の暗幕で潰さず、領域単位でコントラストを作る。

## 6. オブジェクト画像

装備、人物、敵などの主役画像には次を適用します。

- 透明切り抜き、専用マスク、または背景と一体化した専用展示画像を使う。
- 元画像の正方形・長方形の境界を見せない。
- 一覧用サムネイルと主役用画像を必要に応じて分ける。
- 主役用画像を一覧サムネイルの単純拡大で済ませない。
- 画像の周囲に十分な余白を持たせ、名前や占有形状と競合させない。
- 魔法陣や発光は主役を補助する強さに抑える。

必要な切り抜き素材がない場合、先に素材を作ります。四角い画像のまま実装を進めません。

## 7. 文字と情報密度

1280x720論理座標での原則:

- 主要タイトル: 26px以上
- 選択中の名前: 22px以上
- セクション見出し: 14px以上
- 通常本文: 12px以上
- 操作ラベル: 11px以上
- 補助メタ情報: 10px以上

例外的に小さくする場合は、1920x1080キャプチャで実読できることを確認します。

- 一つの行に日本語と英語と数値を詰め込みすぎない。
- 装飾のためだけの英語ラベルを増やさない。
- 文字を画像の細い装飾線へ重ねない。
- 名前、種類、説明、状態の優先順位を崩さない。
- 長文はカード内で折り返し、隣接する操作部品へ入れない。

## 8. 段階実装

一画面を一度に組み上げません。次の順で進めます。

### Gate A: シェル

- 背景
- 遮光
- ヘッダー
- 大領域の分割

ここで撮影し、ホーム画面との同一性を確認します。

### Gate B: 一覧

- カテゴリ
- 通常セル
- 選択セル
- 並べ替え
- スクロール

1件、4件、12件以上で撮影します。

### Gate C: 詳細

- 主役アート
- 名前と説明
- 占有形状
- カード
- 効果

四角い画像境界、枠の重複、文字サイズを確認します。

### Gate D: 動的状態

- hover
- ロック
- 使用中
- 家宝
- 未発見
- 複数形状
- 空状態

各Gateの重大差分を解消するまで次へ進みません。

## 9. 実装規則

### 9.1 画像とUSSの役割

画像を使うもの:

- ゲーム固有のフレーム、タブ、カード、セル
- 状態差分を持つ選択枠、ロック、ページ送り
- アイコン、紋章、オブジェクト絵

USSを使うもの:

- レイアウト、整列、寸法、余白
- 静かな補助面と必要最小限の遮光
- 文字、折り返し、表示制御
- 画像のscale modeと9-slice
- 状態クラスによる画像差し替え

主要部品をUSSの四角だけで完成扱いにしません。
同時に、補助面まで装飾画像へ置き換える必要はありません。

### 9.2 上書き管理

- 正本USS内の既存ルールを理解して修正する。
- 一時的な末尾上書きを積み重ねない。
- 同じルートへ複数世代のクラスを同時に付けない。
- 新しい画面ルートには世代番号ではなく安定した役割名を使う。
- 使われなくなったセレクタは参照を確認して削除する。

保管庫・図鑑の正本USSは
`unity/PackspireUnity/Assets/Resources/UI/PackspireVaultCodexFinal.uss`
です。

### 9.3 共通部品

同じ目的と見た目を持つ部品は、同じ生成メソッド、クラス、素材を再利用します。

- 保管庫と図鑑のLINK効果カード
- 戦闘面・探索面のカード切替
- ロック、ページ送り、選択状態
- 占有形状の3x3グリッド

ただし、共通化のために異なる画風の部品を無理に流用しません。

## 10. 比較と中止条件

各Gateで、参考画像と1920x1080実画面を並べ、必要に応じて半透明で重ねます。

次のいずれかがあれば、そのGateを不合格として修正します。

- 素材を貼り合わせたコラージュに見える。
- ホーム画面より装飾密度が大幅に高い。
- 主役より枠、角飾り、発光が目立つ。
- 同じ意味の紋章やアイコンが二重に見える。
- 主役画像に四角い境界が見える。
- 複数の素材キットで線幅、角、質感が揃っていない。
- 背景の線が文字を横切る。
- 通常状態と選択状態の強弱が逆転している。
- 本文が小さすぎる、または密集している。
- クリック領域と見た目が一致しない。
- 1件と複数件でレイアウトが変形する。

実画面を撮影できない場合は不合格です。推測だけで次のGateへ進みません。

ユーザーまたは品質ゲートが案を却下した場合、その実装を正本として残しません。
変更が未コミットなら、対象画面だけを最後の承認済み状態へ戻すか、明確に無効化してから
次案へ進みます。却下案の画像と原因表は、反面教師として`rejected`表記で保存できます。

## 11. 完了条件

次をすべて満たすまで完成と報告しません。

- ホーム画面から作ったスタイルプロファイルがある。
- 承認済み参考画像が品質ゲートを通っている。
- 物理座標とUSS論理座標の両方を持つ画面仕様がある。
- 領域ごとの素材キット許可表がある。
- Gate AからDまで実画面キャプチャで確認している。
- オブジェクト画像に四角い境界がない。
- 装飾予算と文字サイズを満たしている。
- 必要な動的件数と状態を確認している。
- C#コンパイルが成功している。
- USSの構文エラーと素材参照切れがない。
- 旧セレクタ、未参照素材、一時ファイル、不要な複製を整理している。
- `git status`の変更が依頼対象に限定されている。

完全一致していない項目は、残存差分として具体的に報告します。
